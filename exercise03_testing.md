## TODO 2 – Implementation and Architecture Alignment

### Implementation status

The existing implementation is complete for the first-prototype behavior and remains intentionally compact. `main.py` contains the tkinter startup and view/controller, while `match3.py` contains GUI-independent board and game logic. The required validation still passes. Exercise 2 describes seven logical target components and an incremental ownership refinement; it does not require one class or file per component. The current code is behaviorally aligned, although several target responsibilities remain combined in `Game`, module-level functions, and `Match3App`.

### Reviewed and deliberately left unchanged

- `test_resolution_replaces_only_matched_top_cells`, `test_fully_empty_column_uses_controlled_refill_order`, and `test_gravity_compacts_tiles_down_and_preserves_their_order` call private methods. Moving them would require production refactoring outside Exercise 3.

- Direct `ensure_playable` recovery tests and the public automatic-recovery scenario overlap by domain rule but exercise different boundaries: the former isolates recovery invariants and timing; the latter proves move-to-recovery integration and continued play.
- The 100-seed generation and 10-seed recovery checks retain their two-second assertions because NFR-03 requires those bounds and current runtimes are far below the threshold.
- All four scenario tests genuinely cross coordination, board mutation, rule evaluation, cascade/scoring, and final-invariant responsibilities. None was reduced to a helper-function check.

### Where human judgment was necessary

Human judgment remained essential for behavior that source inspection and non-GUI tests could not establish. A person had to confirm what the window actually rendered, whether rejection and score feedback were understandable, whether Restart and later moves felt usable, and whether resize and close behavior were acceptable. Human review was also needed to recognize assertions that were technically passing but too weak, prevent tests from merely restating implementation assumptions, decide which gaps mattered within prototype scope, and judge usability rather than treating a successful function return as sufficient evidence.

### How prompt quality affected the result

The strongest prompts named the only files that could change, described observable outcomes, required deterministic seeds or fixtures, and stated explicit non-goals such as avoiding GUI automation or production refactoring. Required commands and expected reporting made validation consistent. These constraints reduced accidental scope growth and made it easier to distinguish a real defect from a documentation or coverage gap. Less precise prompts would have encouraged extra tests, implementation-coupled assertions, or unrelated fixes.

### Limitations and risks of agent-generated tests

Agent-generated tests can create false confidence because a green suite does not prove every requirement. Likely failure modes include overemphasizing happy paths, mirroring the current algorithm instead of testing a public contract, choosing fixtures that accidentally avoid difficult states, and overstating integration coverage. GUI behavior is especially easy to miss: logic tests can prove score and board state while saying nothing about highlighting, layout, timing, input locking, or clarity to a player. Traceability also depends on careful reading; matching a requirement and test by similar names is not evidence unless the assertions cover the required result.

### Improvements for a future vibe-coding testing workflow

- Define requirements and acceptance evidence before generating tests, including which evidence must be automated and which can be manual.
- Ask for a risk-based gap review before adding tests so test count is not used as a quality target.
- Require every proposed test to state the observable contract, fixture preconditions, and why existing tests do not already cover it.
- Keep deterministic unit fixtures, but add mutation testing or deliberately broken implementations to check that important assertions can fail for the right reason.
- Plan a small GUI automation layer where practical, while retaining human usability review for visual clarity and interaction quality.
- Record the exact environment, command, date, and result for manual and automated evidence, including explicit “not executed” entries.
- Revisit traceability after every new test so coverage labels describe the evidence accurately rather than assuming that a passing suite means full coverage.
